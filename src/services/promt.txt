# Prompt Antigravity — Implementasi Logic Modul Manajemen Data Pengguna

## 1. Role dan Objective

Act as a senior full-stack developer specializing in React.js, REST APIs, database integration, authentication, and role-based access control.

Implement the complete business logic for the **Manajemen Data Pengguna** module in the existing Marmut Project application.

Use the attached screenshot as the primary UI reference. The screenshot contains two pages:

1. **Data Pengguna** — a user management table.
2. **Tambah Pengguna** — a form to create a new user.

Your task is to make both pages fully functional while preserving the existing UI design, styling, layout, navigation, and reusable components.

**Important:** Do not rebuild the application from scratch. Inspect the existing project, identify its frontend and backend architecture, and integrate the implementation into the current codebase.

Before writing code:

1. Inspect the project folder structure.

3. Inspect the existing backend framework, API endpoints, database configuration, models, migrations, and authentication mechanism.
4. Identify the existing user table and its fields.
5. Check whether login sessions or authenticated user information are already available.
6. Review the existing sidebar and shared layout components.
7. Reuse existing components, services, utilities, and conventions whenever possible.

Do not create a second database connection, duplicate user tables, or introduce a new authentication system if one already exists.

If the project uses Laravel for the backend and React.js for the frontend, maintain that architecture and integrate through the existing API or established communication mechanism.

## 3. Module Overview

The module must support the following features:

- Display a list of users.
- Search users by name or email.
- Display user roles.
- Add a new user.
- Edit an existing user.
- Delete a user with confirmation.
- Validate user input.
- Display success and error notifications.
- Support pagination when needed.
- Enforce role-based permissions.
- Persist changes to the existing database when backend integration is available.

The module must not rely solely on hardcoded mock data for CRUD operations if the project already has a functioning backend.

- Search by full name.
- Search by email.
- Ignore leading and trailing whitespace.
- Make matching case-insensitive.
- Update the displayed results as the user types, with a short debounce if the search is server-side.
- Reset the current page when the search query changes.
- Display an appropriate empty state when no results match.

When the user clicks **Tambah Pengguna**, navigate to the user creation page.

- `/users`
- `/users/create`

### D. Edit User Button

When the user clicks **Ubah**:

1. Open the existing edit page or form according to the application's current architecture.
2. Retrieve the selected user's information.
3. Populate the form with the existing name, email, and role.
4. Allow the user to update editable fields.
5. Submit the changes to the backend.
6. Refresh or update the table after a successful save.
7. Display success or error feedback.

Do not allow a user's password to be overwritten with an empty string when editing their profile.

For password updates, use an optional password field or a separate password-change mechanism, depending on the existing application design.

### E. Delete User Button

When the user clicks **Hapus**, display a confirmation dialog before deleting the user.

The dialog should identify the user being deleted and provide two actions:

- Batal
- Hapus

Deletion logic:

1. If the user cancels, do not change any data.
2. If confirmed, send the delete request to the backend.
3. Remove the user from the table only after successful deletion.
4. Display a success notification.
5. Display an appropriate error if deletion fails.
6. Prevent repeated submissions while deletion is in progress.

Apply these safeguards:

- Prevent a user from deleting their own account if the application requires this restriction.
- Prevent unauthorized users from deleting accounts.
- Protect the last active Superadmin account from deletion.
- Respect existing database constraints and relationships.

The backend must enforce these restrictions; frontend checks alone are insufficient.

## 5. Page: Tambah Pengguna

Recreate the form shown in the attached screenshot.

### A. Form Fields

**1. Nama Lengkap**

- Required.
- Must not be empty or consist only of whitespace.
- Trim unnecessary leading and trailing spaces.
- Apply the existing database's maximum length.

**2. Email**

- Required.
- Must be a valid email address.
- Must be unique among users.
- Normalize whitespace and follow the project's existing email normalization rules.
- If the email already exists, display a useful validation message.

**3. Password**

- Required when creating a new user.
- Use a password input type.
- Provide a show/hide password toggle.
- Apply the existing password security policy.
- Never log, expose, or store plaintext passwords.
- Send passwords securely over HTTPS in production.

**4. Role**

- Required.
- Use a dropdown containing the roles permitted for the current administrator.
- Show the available roles consistently with the screenshot.
- Prevent users from assigning roles they are not authorized to manage.

Do not trust a role value submitted by the browser. Validate authorization on the backend.

### B. Save Button

When the user clicks **Simpan**:

1. Validate all required fields.
2. Display inline validation messages for invalid fields.
3. Prevent duplicate submissions while the request is processing.
4. Submit the user data to the backend.
5. Hash the password on the backend using the framework's secure password hashing mechanism.
6. Store the user in the existing database.
7. Return a success response without exposing sensitive information.
8. Display a success notification.
9. Redirect to the Data Pengguna page after a successful save.
10. Refresh the user list so that the new user appears.

If the backend returns validation errors, map them to the relevant form fields.

If the request fails due to a server or network error, preserve the entered form data and allow the user to retry.

### C. Cancel Button

When the user clicks **Batal**:

- Return to the Data Pengguna page.
- Do not submit the form.
- If the form contains unsaved changes, optionally display a confirmation dialog before discarding them.
